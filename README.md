# IDOR/BOLA Vulnerability Assessment — Banking Web Application

## Overview

This repository documents an authorized security assessment of a deliberately vulnerable banking web application conducted within a controlled training laboratory environment.

The assessment identified an **Insecure Direct Object Reference (IDOR)** vulnerability, also referred to as **Broken Object-Level Authorization (BOLA)**, within the application's transaction-history functionality.

The vulnerability allowed an authenticated test user to manipulate a client-controlled account identifier and access transaction information belonging to another designated test account.

---

## Finding

**Vulnerability:** IDOR / Broken Object-Level Authorization (BOLA)

**Affected Functionality:** Transaction History

**Severity:** High

**CWE:** CWE-639 — Authorization Bypass Through User-Controlled Key

**Authentication Required:** Yes

**Primary Impact:** Unauthorized disclosure of financial transaction information

---

## Assessment Objective

The objective of the assessment was to determine whether the application's transaction-history functionality properly enforced object-level authorization between separate user accounts.

The assessment specifically examined whether an authenticated user could manipulate an account/object identifier and access transaction information belonging to another user.

---

## Methodology

The assessment followed a structured web application security testing process:

```text
Application Reconnaissance
        ↓
Authentication
        ↓
Application Mapping
        ↓
Endpoint Identification
        ↓
HTTP Request Interception
        ↓
Parameter Analysis
        ↓
Authorization Testing
        ↓
Vulnerability Validation
        ↓
Impact Assessment
        ↓
Remediation Recommendations
```

Burp Suite was used to intercept and analyze HTTP requests generated by the application.

---

## Proof of Concept

Two separate authorized test accounts were used during validation.

The transaction-history request contained a client-controlled account/object identifier.

The identifier associated with User A was replaced with the identifier associated with User B while maintaining User A's authenticated session.

The application subsequently returned User B's transaction information.

```text
User A authenticated
        ↓
Transaction request captured
        ↓
Account identifier identified
        ↓
Identifier changed to User B
        ↓
Modified request submitted
        ↓
User B transaction data returned
```

This behavior demonstrated insufficient object-level authorization.

---

## Impact

The primary demonstrated impact was unauthorized disclosure of another user's financial transaction information.

Potential consequences in a real-world environment could include:

* Exposure of sensitive financial activity
* Privacy violations
* Unauthorized account information disclosure
* Customer trust and reputational damage
* Potential regulatory or compliance implications

The assessment demonstrated unauthorized read access. Modification or deletion of another user's transaction data was not demonstrated.

---

## Remediation

The application should implement robust server-side object-level authorization controls.

Recommended controls include:

* Verify the authenticated user's authorization before returning account data.
* Validate account ownership or access permissions server-side.
* Do not treat client-supplied identifiers as proof of authorization.
* Apply authorization checks consistently across sensitive endpoints.
* Reject unauthorized object requests.
* Monitor suspicious repeated authorization failures.
